# Workbench — Universal Instrument Panel Builder

Virtual SCPI instruments with web and Android interfaces. A toolbox-based system where users assemble custom control panels from reusable widgets.

---

## Concept

Build visual indicators (meters, lights, charts, graphs, warning lights, virtual LCD displays) and control functions (switches, knobs, buttons, sliders) that can be combined into custom instrument panels. Support both SCPI and MQTT interfaces.

Users compose panels from a widget library via JSON/YAML config files. Panels can monitor/control physical bench instruments (SSA, SDG, IC-7300) or virtual instruments built specifically for this framework.

---

## Feasibility Assessment

### Easy parts

1. **Widget library** — Analog meters, bar graphs, LEDs, switches, sliders, XY plots, waterfall displays are standard UI components. React/Vue for web, Jetpack Compose for Android.
2. **JSON/YAML config format** — Define panel layout, widget types, bindings, styling in a file. Hand-editable or generated by a GUI builder.
3. **MQTT integration** — Natural fit. Widgets subscribe to topics (`bench/ssa/freq`, `bench/dmm/voltage`), instruments publish, UI updates live. Low latency, scales to 100+ widgets.
4. **SCPI integration** — Slightly harder (polling vs push), but manageable. Backend polls SCPI commands at configured intervals, pushes results to frontend via WebSocket.

### Medium-hard parts

1. **Bidirectional controls** — User drags a slider, backend sends SCPI command, instrument changes, but now the widget needs to reconcile user input vs instrument feedback. Conflict resolution required.
2. **Layout engine** — Drag-and-drop builder is complex. Start with grid-based or absolute positioning via JSON, add GUI builder later.
3. **Performance at scale** — 20 widgets polling 20 instruments at 100ms = 200 requests/sec. MQTT scales better (pub/sub, no polling). SCPI needs connection pooling and rate limiting.

### Hard parts

1. **State synchronization** — Multiple clients (web + Android + SCPI external tools) all controlling the same instrument. Who wins when they conflict?
2. **Configuration complexity** — Power users want thresholds, color gradients, formulas (`display = (MEAS:VOLT? - 5) * 2`), unit conversions. Simplicity vs flexibility tradeoff.

## Recommended Architecture

```
Instrument Core (Python backend)
    ├─ SCPI TCP Server (port 5025) ← external clients (LabVIEW, MATLAB)
    ├─ MQTT Broker integration (mosquitto) ← pub/sub for widgets
    ├─ WebSocket Server (port 8001) ← real-time web UI updates
    └─ HTTP Server (port 8000) ← serve web UI + REST API

Widget Config (JSON/YAML)
    - Widget type (analog_meter, led, switch, slider, waterfall)
    - Binding (SCPI command or MQTT topic)
    - Display properties (range, units, color thresholds, position)
    - Update rate (100ms, 1s, on-change)

Web UI (React/Vue)
    - Loads config, renders widgets dynamically
    - Subscribes to WebSocket or MQTT topics
    - Sends control commands (button press → SCPI write or MQTT publish)

Android UI (Kotlin/Jetpack Compose or Flutter)
    - Same widget library, native rendering
    - Same config format (JSON/YAML)
    - Direct MQTT connection or HTTP → backend bridge
```

## SCPI vs MQTT

| Use Case | SCPI | MQTT |
|----------|------|------|
| Control existing instruments (SSA, SDG) | ✅ Yes | ❌ No (unless bridged) |
| Virtual instruments you're building | ✅ Yes | ✅ Yes (easier for UI binding) |
| Real-time monitoring (100ms updates) | ⚠️ Polling overhead | ✅ Natural pub/sub |
| External tool integration (LabVIEW) | ✅ Standard protocol | ⚠️ Requires MQTT library |
| Multi-client coordination | ⚠️ No pub/sub, manual sync | ✅ Built-in broadcast |

**Recommendation:** Support **both**. Virtual instruments expose SCPI (for compatibility with existing tools) *and* publish to MQTT (for efficient UI updates). Backend bridges between them.

## Phased Development Plan

### Phase 1: Core widget library (read-only monitoring)

**Goal:** Prove the concept with monitoring-only panels.

**Widgets (10 types):**
- Analog meter (needle gauge)
- Bar graph (horizontal/vertical)
- LED indicator (single color or RGB)
- Numeric display (7-segment LCD style or plain text)
- Line chart (time-series, scrolling)
- XY plot (scatter/line)
- Text LCD (streaming text, terminal-style)
- Waterfall display (spectrum/time)
- Compass (directional indicator)
- Gauge cluster (multi-meter composite)

**Features:**
- JSON config format (hand-edited)
- MQTT-only bindings (subscribe to topics)
- Web UI renders dynamically from config
- Python backend bridges SCPI instruments → MQTT

**Example use case:** Monitor SSA frequency, DMM voltage, IC-7300 S-meter on one screen.

**Deliverable:** `workbench-server.py` (Python backend) + `workbench-ui/` (React/Vue web app) + example config files.

---

### Phase 2: Bidirectional controls

**Goal:** Add user input widgets that send commands back to instruments.

**New widgets (5 types):**
- Toggle switch (on/off, SPDT visual)
- Push button (momentary)
- Rotary knob (continuous or stepped)
- Slider (horizontal/vertical, linear or log scale)
- Text input (send arbitrary SCPI commands or MQTT messages)

**Features:**
- Widgets can write SCPI commands or publish MQTT messages
- Read-after-write confirmation (widget updates after instrument confirms)
- Conflict resolution (multiple clients changing same parameter)

**Example use case:** Slider controls SDG frequency, button triggers SSA sweep, toggle enables PSU output.

**Deliverable:** Updated widget library + bidirectional MQTT/SCPI handlers.

---

### Phase 3: SCPI integration

**Goal:** Seamlessly integrate existing SCPI instruments into the panel system.

**Features:**
- Backend polls SCPI commands at configurable intervals
- Results published to MQTT topics
- Widgets don't care if data came from SCPI or native MQTT — abstraction layer
- Connection pool for multiple SCPI instruments
- Rate limiting to avoid overwhelming instruments

**Example config:**
```yaml
instruments:
  ssa:
    type: scpi
    host: 10.1.1.60
    port: 5025
    mappings:
      - command: ":CALC:MARK1:X?"
        topic: bench/ssa/marker1_freq
        interval: 500ms
        parse: float
      - command: ":CALC:MARK1:Y?"
        topic: bench/ssa/marker1_level
        interval: 500ms
        parse: float
```

**Widget subscribes to `bench/ssa/marker1_freq`**, doesn't know it came from SCPI.

**Deliverable:** SCPI→MQTT bridge module + example configs for SSA, SDG, SDM, SPD.

---

### Phase 4: Drag-and-drop config builder

**Goal:** Web-based panel designer so users don't hand-edit JSON.

**Features:**
- Drag widget from palette, drop on canvas
- Click widget → property editor (binding, range, color, thresholds, units)
- Live preview (connect to real instruments, see data flow)
- Save/load/export configs
- Template library (common panel layouts: HF station, VHF/UHF, battery lab, RF test bench)

**UI inspiration:**
- Grafana dashboard editor (panel library, drag-drop, property inspector)
- Node-RED (flow-based, but visual layout concepts apply)
- Home Assistant Lovelace editor

**Deliverable:** `workbench-designer/` web app + template gallery.

---

### Phase 5: Android app

**Goal:** Native mobile panel viewer/controller.

**Features:**
- Native app (Kotlin/Jetpack Compose or Flutter)
- Loads same JSON configs as web UI
- Direct MQTT connection (efficient, low latency)
- Optional HTTP bridge mode (if MQTT not exposed to internet)
- Offline mode (last known values cached)
- Notifications (threshold alerts, instrument errors)

**Example use case:** Monitor HF station SWR and temperature from phone while outside. Tap button to trigger antenna tuner.

**Deliverable:** `workbench-android/` app + Google Play release.

## Why This Is Worth Building

1. **One builder → infinite panels.** No coding required to create a new layout, just config.
2. **Shareable configs.** Post on forums, GitHub. "Here's my HF station panel JSON."
3. **Lowers barrier.** Non-programmers can assemble monitoring dashboards.
4. **Unifies the bench.** 10 instruments + 5 ESP32 controllers → one control room interface.
5. **Protocol bridge.** SCPI instruments become MQTT devices, enabling home automation integration (Home Assistant, Node-RED).
6. **Mobile-first option.** Android app makes remote monitoring/control viable without VNC/SSH.

## Initial Widget Library (Phase 1)

### Analog Meter
- **Visual:** Round gauge with needle, colored zones (green/yellow/red)
- **Config:** `min`, `max`, `units`, `zones` (thresholds), `needle_color`
- **Binding:** MQTT topic or SCPI command (backend polls)
- **Use case:** S-meter, SWR, voltage, current, temperature

### Bar Graph
- **Visual:** Horizontal or vertical filled bar, optional gradient
- **Config:** `min`, `max`, `orientation`, `color`, `thresholds`
- **Binding:** MQTT topic or SCPI command
- **Use case:** Signal strength, battery charge, power output

### LED Indicator
- **Visual:** Single LED circle, configurable color(s)
- **Config:** `on_color`, `off_color`, `blink_rate` (optional)
- **Binding:** MQTT boolean topic or SCPI query (parse as 0/1)
- **Use case:** PTT active, relay state, alarm condition

### Numeric Display
- **Visual:** 7-segment LCD or plain text digits
- **Config:** `precision`, `units`, `font_size`, `color`
- **Binding:** MQTT topic or SCPI command
- **Use case:** Frequency readout, voltage, distance, GPS altitude

### Line Chart
- **Visual:** Scrolling time-series graph, multiple traces supported
- **Config:** `history_seconds`, `y_min`, `y_max`, `traces` (list of topics/colors)
- **Binding:** Multiple MQTT topics or SCPI commands
- **Use case:** Voltage vs time, S-meter trends, temperature logging

### XY Plot
- **Visual:** Scatter or line plot, X and Y from separate sources
- **Config:** `x_min`, `x_max`, `y_min`, `y_max`, `x_topic`, `y_topic`
- **Binding:** Two MQTT topics or SCPI commands
- **Use case:** I-V curves, constellation diagrams, antenna patterns

### Text LCD
- **Visual:** Monospace text display (think 16×2 character LCD)
- **Config:** `rows`, `cols`, `font`, `scroll_mode` (wrap, scroll, truncate)
- **Binding:** MQTT topic (string payload) or SCPI query
- **Use case:** GPS NMEA sentences, instrument status messages, log tail

### Waterfall Display
- **Visual:** Time vs frequency/parameter heatmap (vertical scrolling)
- **Config:** `width_bins`, `history_rows`, `color_map`, `z_min`, `z_max`
- **Binding:** MQTT topic (array payload) or SCPI trace query
- **Use case:** Spectrum analyzer waterfall, RTL-SDR, temperature profile over time

### Compass
- **Visual:** Circular compass rose with needle
- **Config:** `cardinal_labels` (N/S/E/W), `needle_color`
- **Binding:** MQTT topic (degrees, 0–360) or SCPI heading query
- **Use case:** Antenna rotator azimuth, GPS heading, wind direction

### Gauge Cluster
- **Visual:** Multiple small gauges in a grid (car dashboard style)
- **Config:** Array of sub-gauges (each with own binding, range, label)
- **Binding:** Multiple MQTT topics or SCPI commands
- **Use case:** PSU voltage+current+power in one widget, GPS speed+alt+heading

## Example Panel Config (Phase 1)

```yaml
panel:
  title: "HF Station Monitor"
  layout:
    grid:
      rows: 3
      cols: 3

  widgets:
    - type: analog_meter
      position: {row: 0, col: 0}
      label: "S-Meter"
      binding:
        mqtt_topic: "bench/ic7300/strength"
      config:
        min: 0
        max: 9
        units: "S"
        zones:
          - {max: 3, color: red}
          - {max: 7, color: yellow}
          - {max: 9, color: green}

    - type: numeric_display
      position: {row: 0, col: 1}
      label: "Frequency"
      binding:
        mqtt_topic: "bench/ic7300/frequency"
      config:
        precision: 3
        units: "MHz"
        font_size: 24

    - type: led_indicator
      position: {row: 0, col: 2}
      label: "PTT"
      binding:
        mqtt_topic: "bench/esp32/ptt/state"
      config:
        on_color: red
        off_color: gray

    - type: line_chart
      position: {row: 1, col: 0, colspan: 3}
      label: "S-Meter History"
      binding:
        mqtt_topic: "bench/ic7300/strength"
      config:
        history_seconds: 60
        y_min: 0
        y_max: 9

    - type: bar_graph
      position: {row: 2, col: 0}
      label: "SWR"
      binding:
        mqtt_topic: "bench/esp32/swr/ratio"
      config:
        min: 1.0
        max: 3.0
        orientation: horizontal
        thresholds:
          - {max: 1.5, color: green}
          - {max: 2.0, color: yellow}
          - {max: 3.0, color: red}

    - type: gauge_cluster
      position: {row: 2, col: 1, colspan: 2}
      label: "Power Supply"
      binding:
        - mqtt_topic: "bench/spd3303x/ch1/voltage"
          label: "V"
          min: 0
          max: 32
        - mqtt_topic: "bench/spd3303x/ch1/current"
          label: "A"
          min: 0
          max: 3.2
```

## SCPI Bridge Config Example (Phase 3)

```yaml
# scpi-bridge.yaml
# Maps SCPI instruments to MQTT topics

instruments:
  ssa3032x:
    host: 10.1.1.60
    port: 5025
    mappings:
      - scpi: ":CALC:MARK1:X?"
        mqtt: "bench/ssa/marker1_freq"
        interval: 500ms
        parse: float
        scale: 1e-6  # Hz → MHz

      - scpi: ":CALC:MARK1:Y?"
        mqtt: "bench/ssa/marker1_level"
        interval: 500ms
        parse: float

      - scpi: ":FREQ:CENT?"
        mqtt: "bench/ssa/center_freq"
        interval: 1s
        parse: float
        scale: 1e-6

  sdm3045x:
    host: 10.1.1.63
    port: 5025
    mappings:
      - scpi: ":MEAS:VOLT:DC?"
        mqtt: "bench/dmm/voltage"
        interval: 200ms
        parse: float

      - scpi: ":MEAS:CURR:DC?"
        mqtt: "bench/dmm/current"
        interval: 200ms
        parse: float

  ic7300:
    type: hamlib_rigctld
    host: localhost
    port: 4532
    mappings:
      - rigctl: "f"
        mqtt: "bench/ic7300/frequency"
        interval: 500ms
        parse: float
        scale: 1e-6  # Hz → MHz

      - rigctl: "l STRENGTH"
        mqtt: "bench/ic7300/strength"
        interval: 200ms
        parse: int
```

Backend reads this config, opens connections to all instruments, polls at specified intervals, publishes to MQTT. Widgets subscribe to `bench/ssa/marker1_freq` and don't care it came from SCPI.

## Technology Stack Recommendations

### Backend (Python)
- **Framework:** FastAPI (async, WebSocket support, auto-docs)
- **MQTT:** paho-mqtt (client library)
- **SCPI:** Raw TCP sockets via `rf_bench.*` drivers (already built)
- **Config:** PyYAML or tomli for TOML parsing
- **Serving:** Uvicorn (ASGI server)

### Web UI
- **Framework:** React (larger ecosystem) or Vue 3 (simpler, faster to prototype)
- **Charts:** Plotly.js (interactive, wide widget variety) or Chart.js (lightweight)
- **MQTT:** mqtt.js (browser WebSocket client)
- **Styling:** TailwindCSS (utility-first, rapid prototyping)

### Android
- **Language:** Kotlin
- **UI:** Jetpack Compose (modern declarative UI)
- **MQTT:** Eclipse Paho Android client
- **Charts:** MPAndroidChart or Vico

### MQTT Broker
- **Mosquitto** (lightweight, standard, easy to install)
- Run on same host as workbench-server or dedicated LAN broker
